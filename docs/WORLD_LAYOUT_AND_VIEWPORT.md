## 2. Minimal Godot 4 implementation recommendation (PROPOSED)

- Keep the frozen A runtime scene ownership: `GameRoot` → `World: Node2D` plus `UI: CanvasLayer`. Use **one ordinary 2D viewport**. Avoid a separate `SubViewport`, viewport texture pipeline or independent interactive UI game state to carve out the left area.
- Establish an editable **`ui_safe_rect`** in logical canvas coordinates for the persistent left band, and a **`world_visible_rect`** for the right-hand area. Their widths should come from the chosen viewport/art fit, **not** hardcoded screenshot pixel ratios. Draw temporary solid rectangles in Milestone 0. UI `Control` anchors should track the logical viewport dimensions.
- Place the world contents using **either** an offset/scaled `World` transform **or** a single `Camera2D` framing scheme; choose **one** and document it. World coordinates and tile indices remain independent of the screen offset. Do not shift the world by editing each fixture's logical tile coordinates.
- Use authored `TileMapLayer` and object/marker scenes with stable IDs for kitchen work areas, tables, utility purchase slots, three driver pickup spots, overflow driver queue, diner waiting anchors and online acceptance station. Do not construct the final game map by interpreting colors/pixel boundaries in the sketch.
- Route world clicks using Godot's actual **viewport-to-world** transform; e.g., if a click is in `ui_safe_rect`, do not forward it to kitchen click routing; otherwise convert correctly to world/tile coordinates before hit testing. Do not implement competing pointer routers. Buttons/modals capture UI events; purely decorative ring overlays ignore mouse input. No `Control` should steal world clicks through invisible full-rect backgrounds.
- Dine-in/outside driver/customer icons and countdown rings are rendered from authoritative B/C read-only views. Convert world anchors into UI canvas coordinates for popups. Clamp/flip the **station dialogue inside visible screen bounds**, preferably avoiding the left persistent UI safe band during regular service. Temporary planning/dialog/result panels **may deliberately overlap world**; while open, they block clicks through to stations/floor and do not pause the service clock.
- Maintain the established mouse-travel challenge. Do not auto-move interaction targets into the UI band or introduce a screen-fixed cooking menu to avoid distance. Retain the physical online acceptance station and the actual driver click targets.
- The existing **640×360 logical, 1280×720 display** suggestion is a **candidate only**. For perspective: 13×9 * 32px would occupy approximately **416×288 logical pixels for the gridded area**. This is *illustrative calculation only*, not a locked world size. A left UI band, margins, queue sprites, popups and top HUD may require adjusted framing or a different logical resolution; verify before approving UI art sizes. Prefer simple integer scaling and nearest filtering that respect the pixel art. Avoid continuously resizing the world with arbitrary noninteger scaling when switching phases.

## 3. Milestone 0 visual blockout and exact checks

1. Draw distinct placeholder rectangles for **left UI**, **dine-in waiting lane**, **restaurant world**, **three online driver pickup spots** and **online overflow**. Use approximate source arrangement but author actual scene positions, not code constants. Reserve space for kitchen stations and dining tables from the starter kit. Validate whole playable area on a real game window, not only editor zoom.
2. At a chosen trial resolution, put a representative full-width cash/Day7 bar/day/count in left HUD. Confirm legibility and no overlap with waiting patrons; the user should never need to infer player position from behind the panel.
3. Simulate a worst-case visible state: several waiting dine-in patrons with 100s rings, at least 3 at-spot drivers plus one outside driver with 60s rings, one 100s delivery marker, a held-item icon and the **longest actual station ghost-command dialogue**. Verify sprite/label collisions, right/top/bottom clipping, and that each *serveable* target remains clickable. If it fails, adjust layout/viewport before proceeding; do not solve by removing required indicators.
4. Click across boundaries: left-band empty pixels or buttons must **never teleport**; the first accessible floor tile next to waiting lane **does teleport**. Click a far-away station after world offset/zoom: player must land on a valid cardinal neighbor and that target alone becomes selected. Buttons/purchase modals never trigger world movement.
5. Open Menu or Belanja and then RESULTS: panels may temporarily cover the world but **must** capture focus/input in their actual bounds. Service time keeps running during Belanja. On returning to service, focused station/typing feedback must remain deterministic.
6. Check at an exported desktop window size and at a resized/letterboxed size if the selected Godot project settings allow resizing. Nearest-pixel readability, correct cursor mapping and unclipped dialogue take priority over preserving a specific unverified viewport number.

**Acceptance condition:** layout is visibly divided and fully usable without changing any confirmed core gameplay. Exact final tile counts and UI safe-band width are finalized only after the pixel and UI artists' assets are fitted. No new gameplay approval is required for simple scene-coordinate adjustments.
