# B — Movement, Typing, Kitchen, Food and Inventory (revised v2.0)

**Owner:** `KitchenController`. Uses the sole canonical contract in `../ARCHITECTURE.md` and confirmed rules in `../SHARED_BASELINE.md`. Replaces B v1.1's obsolete online-station serving, unspecified selected-container APIs and physical-only close references. State is ephemeral except installed fixture raw fridge contents and finite plate registry.

## 1. Components and data (Godot 4)

- `kitchen_controller.gd`: world click routing, selected target, player tile, **only** accepted-prefix parser, context commands, held aggregate, work-table slots, storage, plate ledger, shipment reservations and day reset. No new autoload, global inventory singleton, separate keyboard parser, player walking/pathfinding or crafting engine.
- `food_item_state.gd` (`RefCounted` runtime): `item_id`, `plate_id` empty or unique, `parts: Array[FoodComponentState]`, `location=HELD|WORK_TABLE|COOKER_OUTPUT|CONSUMED`, `work_table_id` as relevant. `FoodComponentState`: static `ingredient_id` + processed steps; from RAW `beras` → WASHED → COOKED_RICE; `ayam/tempe/telur/sapi` RAW→COOKED; `sayur` RAW→CHOPPED, RAW→COOKED, CHOPPED→CHOPPED_AND_COOKED. These transforms are instantaneous on valid typed completion. No reverse or forced recipe-specific plating sequence.
- `ingredient_def.gd` + `.tres`: stable ingredient ID, Indonesian display name, valid preparation transitions. `recipe_def.gd` + `.tres`: stable recipe ID, Indonesian name/icon key, array of exact `{ingredient_id, required_preparation_state}` part requirements, and uniqueness checks. A plate must contain **exactly** these requirements (multiset) with no extras; no menu-specific hardcoded code paths.
- `StorageUnit` (B runtime keyed by actual installed `storage_unit_id`), internal `StorageSlot {ingredient_id or empty, quantity, capacity}`, pending reserved quantities keyed by `purchase_id`. Fridge = **2 independent slots ×3**, box = **3 independent slots ×5**; same raw ingredient can fill more than one slot. Each purchase chooses **one actual container**; never distribute among others. No cooked/washed/chopped item may be put in storage.
- `PlateRecord` keyed by unique `plate_id`, with `origin_rack_id` and `location=RACK|HELD|WORK_TABLE|CUSTOMER_TABLE|WASHER_DIRTY`. No additional mutable “clean plate count” alongside the ledger. Rack grants `plates_per_rack` unique records once; multiple racks add records, if safely removed they remove own plate IDs only. Washer is unbounded but wash acts on one plate at a time.
- `ShipmentRecord` keyed by D-owned `purchase_id`, pinned to `storage_unit_id`, `{ingredient_id,quantity, due_at,status:PENDING|DELIVERED|CANCELED}` and reserved physical capacity. One purchase cannot get refunded and delivered; D owns money and actual payment value.

## 2. Starting interaction targets and authoritative typing behavior

| Physical target | Click action | Typed token(s), scoped by valid held/context state | Effect |
|---|---|---|---|
| Floor | Teleport only | none | Destination must be accessible; no implicit station selection |
| Fridge / box | Teleport cardinal-adjacent, select | Ingredient names: `beras`,`ayam`,`sapi`,`tempe`,`sayur`,`telur` (when stock exists) | One RAW unit into **empty hand**; decrement selected unit/slot exactly once |
| Stove/kompor | Teleport/select | `goreng` | Held legal ingredient RAW (or prepared veg after `potong`) → cooked; instant |
| Rice cooker | Teleport/select | `masak` (with held WASHED rice), `nasi` (with empty hand and output) | Immediately deposit washed rice into a **single** cooker output; retrieve one COOKED_RICE; no arbitrary infinite cooked output |
| Washer/wastafel | Teleport/select | `cuci` | With held RAW rice: mark WASHED; with empty hand + dirty plates: wash exactly one into held clean plate. Same physical starter station, one parser |
| Work table — staging surface | Teleport, one-click contextual | no typed word | One slot: place held item; pick up staged item into empty hand; prepared loose component merges into staged plated aggregate; disallow loose-to-loose merging |
| Work table — chopping hotspot | Teleport/select (separate target region of **same physical** table) | `potong` | Held raw vegetable → CHOPPED immediately; does not auto-stage item when selecting chop region |
| Plate rack | Teleport, one-click | none for pickup | Empty hand takes one finite clean plate (as one empty plated aggregate); optional second click returns empty clean held plate |
| Dining table | Teleport/select | `saji`, `bersihkan` as available | Dispatch `saji` to C `try_serve_table(table_id,held_id)`; cleaning to C `try_clean_table`. No food staging |
| Online acceptance station | Teleport/select | `terima` (while C says eligible) | C creates a voluntary accepted order & a driver with 60s; **cannot `saji` here** |
| Online driver in pickup spot | Teleport/select exact `driver_id` | `saji` | Dispatch to C `try_serve_driver(driver_id,held_id)`; only when spot assigned |
| Online driver in outside overflow | Click may indicate waiting state only | no serving action | Cannot serve, even if exact dish is held; no false food consumption |
| Trash | Teleport, mouse activation | none | Discard food; preserve same reusable empty plate in hand if item was plated (explicit reversible default) |

**Input flow:** World object hitboxes take priority over floor, one target per left click; UI consumes modal clicks before world. Floor click never interacts; target click from any distance teleports to a legal **cardinal neighbor** and selects/executes its click action in the *same click*. Pick nearest walkable cardinal neighbor with deterministic tie order. If no free neighbor or invalid phase, leave food/stock unchanged and display a localized failure. CLICK ANYWHERE ELSE clears accepted typed prefix (does not erase staged food). PLANNING allows clicking storage for `Belanja` and fixture UI, but never retrieves/prepares kitchen items. All click selectors use the common router, not E's own object hit-test.

**Keyboard prefix FSM:** With eligible selected target and SERVING, compute currently valid command words from **current** B/C context. Initially `prefix = ""`; on `InputEventKey` unicode char (no echo/modifier), normalize case, only append if at least one valid command starts with new prefix. Otherwise ignore it and inform E to shake prompt. On exact full-word match execute **immediately** (no Enter), clear prefix, keep target selected for another command. On click elsewhere clear prefix. Proposed keys: Backspace removes one accepted letter, Escape clears; never accept key repetition `event.echo`. Reject command collisions where one valid full word is strict prefix of another at the **same** context; validate command set up front. E shows B's actual available commands, not its own list. Only one system reads gameplay keystrokes; buttons/purchase quantity fields have modal focus and do not leak keys to parser. Shopping does **not** stop any service timer.

## 3. Food/plate transitions and invariant

- **One hand item only.** Retrieving stock with occupied hand fails before stock mutation. Taking a plate requires empty hand. A single plated aggregate can contain multiple components but consumes **one** work table slot and one held slot. A loose component may be cooked/chopped while held. Cooking doesn't create an extra item; rice cooker output is the single exception and consumes held WASHED rice until retrieved with empty hand.
- Work table with no staged item + holding item: one click stages it. Work table with staged item + empty hand: one click picks it up. Work table with plated aggregate + held legal loose prepared component: one click **merges** component into that one aggregate, invalidates consumed loose object, frees hand. Work table with loose ingredient + held loose ingredient: **reject**; only plating merges, never accidental combination. Each individual work surface holds **one** item or plated aggregate; kitchen prep/chopping is on separate hit target so click doesn't unintentionally stage a vegetable being chopped.
- New dish must begin with **plate**. Plating order can vary across valid prepared ingredients. Recipe validation uses exact multiset of ingredient+preparation-state requirements; subsets are unfinished, supersets or wrong states do not match, unplated food cannot serve. Wrong dish can go to trash; trash removes food components, retaining same empty clean plate (reversible default, no plate duplication). No implicit food reuse across two orders.
- On dine-in `saji`, C validates exact seated waiting order/table and deadline before B `try_consume_serving_item(item_id,recipe_id,DINE_IN,table_id)`. B atomically removes ONE plated food aggregate and marks original plate at customer table, C owns order and eating. After diner leaves DIRTY, B receives `move_cleaned_table_plate_to_washer(table_id)` only on C validated cleaning; plate becomes WASHER_DIRTY once, dining table becomes CLEAN_VACANT in C. `cuci` washer with empty hand removes **one** dirty plate and creates held empty plated aggregate referencing that plate ID, not a new physical plate.
- On online driver `saji`, C validates exact at-spot driver/order, calls B `try_consume_serving_item(item_id,recipe_id,ONLINE,&"")`. B consumes food and returns the **same** reusable plate to its clean rack supply immediately. No diner eating, table dirt or dirty washer plate. Repeated success cannot create extra clean plates.
- At day close, raw fridge contents survive; box stock, all held/staged/cooker output/prepared food vanish; every still-owned plate is restored to a clean surviving rack; washer queue empty; no actual order or money mutation from kitchen reset. Missing sales/stock cannot be silently refilled.

|---|---|---|
| `nasi_telor` | Nasi Telor | `beras:COOKED_RICE` + `telur:COOKED` |
| `nasi_ayam` | Nasi Ayam | `beras:COOKED_RICE` + `ayam:COOKED` + `tempe:COOKED` |
| `nasi_komplit` | Nasi Komplit | `beras:COOKED_RICE` + `ayam:COOKED` + `tempe:COOKED` + `sayur:CHOPPED` + `telur:COOKED` |

One new dish per day is planned; four+ later recipes are **CONTENT PENDING**. Their inclusion must be purely data additions (resource + D economy/unlock entry + icon), never a new case statement in B/C. `sapi` is a permitted ingredient for future dishes but does not automatically form a fourth current recipe. Exact display spelling and typed vocab should remain centrally editable; ID stability matters more than spelling.

## 5. Storage and delivery transactions (D money ↔ B physical stock)

1. User clicks a specific physical installed storage container (`storage_unit_id`) and presses `Belanja`, selects ingredient, quantity. D verifies money/phase. B `can_receive_stock(id, qty, target)` previews selected container capacity; B `reserve_incoming_capacity(purchase_id, id,qty,target)` *revalidates* target slots including prior reservation amounts. Duplicate ingredient IDs can fill multiple slots; fill matching partial slot then empty slot, stable slot order. **All or nothing; never spill to another fridge/box.**
2. D records paid amount and subtracts cash once (after reservation). In PLANNING B `receive_stock(purchase_id,id,qty,target)` immediately uses reservation and updates selected slots. In SERVING B `schedule_delivery(purchase_id,id,qty,target,due_at=now+100.0)` and holds capacity. `advance_service_time(now)` delivers once when due, removes reservation and marks shipment delivered. Do not use Godot Timer nodes in addition to root clock.
3. On service close, only still PENDING deliveries are canceled by B; return distinct paid `purchase_id` IDs to D, release reservation, and D refunds actual paid cash from ledger *once*. A delivered shipment at exact boundary (root processes due deliveries **before** close check) is not refundable. Storage sale in planning fails if any raw stock or reserved delivery exists; racks require their plates safe/clean.
4. Fridge raw stock carries over; box raw stock clears. No prepared or plated item goes into storage. Purchase to a fridge or box works equally; UI always shows actual chosen target and actual per-slot occupancy.

## 6. Dependencies and public API

Exact signatures in `../ARCHITECTURE.md` §5, especially `on_interactable_clicked`, `accept_typed_character`, `try_consume_serving_item(item_id,recipe_id,kind,table_id)`, `move_cleaned_table_plate_to_washer(table_id)`, and all **storage_unit_id-bearing** capacity/receipt/reservation/delivery methods. B sends requests to C for online acceptance/driver serve/table serve/clean; D owns cash and fixture purchases; C owns driver location and order status; E owns visuals/focus. B never creates a duplicate “selected online order popup” or serves online food at acceptance station.

**Godot implementation notes:** one main `KitchenController` is enough. Use `Area2D.input_event` or a single global router, not both; tile floor in `_unhandled_input`. `ui` overlays consume clicks and don't call B while modal. Keep `.tres` definitions immutable during runtime. Validate station and item states before changing either. Signals occur *after* mutation, so UI refreshes authoritative views. Avoid game state changes in animation completion callbacks.

## 7. Acceptance tests (manual or tiny test scene)

1. **Click routing:** floor tile only moves; object click from far away lands on **cardinal** floor neighbor and activates once; blocked neighbor rejects; clicking elsewhere resets `prefix` but not staged food. UI modal never triggers floor teleport.
2. **Typing:** at fridge `ayam`, keystrokes `a y x a m` accept `ay`, ignore `x`, then only valid continuation; on full `ayam`, exactly **one** raw stock item removed. Invalid command, hand full, wrong station leave stock unchanged. No Enter action.
3. **Composite:** clean plate staged on work table; cooked `tempe`, cooked chicken and cooked rice added in ANY order produce exact `nasi_ayam`. Extra/missing/raw ingredient fails. A second loose item cannot occupy same work slot. Player interrupts and resumes without losing partial food.
4. **Wash/chop:** with held RAW `beras`, click washer and type `cuci` → WASHED. With empty hand and one dirty washer plate, same washer `cuci` → unique clean plate held. With held RAW `sayur`, select chopping hotspot and `potong` → CHOPPED **without staging/moving** ingredient.
5. **Plate ledger:** one plate travels rack → held → stage → customer → dirty washer → held → rack, plate total unchanged. Online serve returns same plate clean directly; trash wrong plated meal preserves one unique plate, no duplication. Rack grants its configured amount exactly once.
6. **Storage slots:** fridge stores `[ayam×3,ayam×3]`, seventh rejected; box `[beras×5,beras×5,beras×5]`, sixteenth rejected; different selected container receives nothing. Pending reservation blocks overbooking.
7. **Delivery:** planning immediate; service 100.0s after paid accepted purchase, no early retrieval; pending at close cancels and refunds once; delivered at/before same tick as close does not. Overnight raw fridge persists, box/work food clears, plates reset CLEAN.
8. **Driver fulfillment:** `saji` at online accept station does nothing; `saji` on in-spot physical driver exact-order serves, outside-driver attempt fails; dining-table `saji` targets that table's order, not arbitrary equal-recipe order.
9. **Idempotency:** duplicate stock delivery, order serving, plate move/washer, day reset, refund cannot create food, reusable plates or money. No interaction during CLOSING/RESULTS.
